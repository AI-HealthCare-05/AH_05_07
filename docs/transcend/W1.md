## W1 visible outcome

A deliberately small Lab-only test world renders one qualified bear (or a local
surrogate until the asset step is ready) from a conventional third-person camera
positioned above and behind the actor.

The user can move through a fixture containing:

- spawn/flat ground;
- a wall;
- a slope;
- a step/stair fixture;
- a narrow/camera-obstruction fixture;
- one synthetic interaction destination;
- an out-of-bounds recovery region.

Desktop keyboard input and mobile touch input both produce normalized movement
intent. The camera supports yaw/pitch follow behavior and shortens safely around
obstructions. The same synthetic destination remains reachable through a
semantic DOM control without 3D locomotion.

Visual polish, the seven-landmark Living Week map and real product data are not
W1 success criteria.

## Minimal implementation rules

1. Keep W1 inside `web/transcend-lab/` until the program's world-client gate
   passes.
2. Do not make React state the simulation clock and do not call React state
   setters every frame. High-rate mutable simulation state stays in the Lab
   runtime/owned objects; React receives only bounded snapshots/status needed by
   controls and diagnostics.
3. Start with the fewest modules needed by the next test. Do not pre-create a
   generic WorldRuntime/RendererPort/PhysicsPort/AssetRuntime framework merely
   because later milestones may need one.
4. Keep CSS-pixel Arena/Anchor experiments separate from 3D metre-based
   WorldSpace. Explicit adapters may project between spaces; coordinates are not
   silently interchangeable.
5. Physics owns actor world translation. Animation owns visual pose. W1 does not
   authorize root-motion locomotion.
6. Visibility/stop/reset invalidates high-rate work; returning from a hidden tab
   must not replay accumulated simulation time.
7. World input suspends while a semantic interaction panel has focus/open
   ownership. Pointer cancel/lost capture, blur and visibility changes must leave
   zero stuck movement intent.
8. A WebGL/context failure leaves semantic controls usable.

## Physics dependency gate

Rapier is a candidate, not yet W1 authority. Add it only in a separate
protected-boundary task because it is a new dependency.

The spike should prefer the normal browser/Vite `@dimforge/rapier3d` package
before considering the larger compatibility package. It must prove:

- Lab-only executable import;
- no Rapier/WASM module in the normal product build graph/output;
- a bounded kinematic character controller fixture for wall/slope/step/ground;
- explicit controller/world cleanup across repeated stop/reset;
- stale initialization cannot revive a stopped Lab generation.

Ordinary integration friction is not an engine-switch trigger. Escalate to a
Babylon/Havok bake-off only if bounded evidence shows a structural correctness,
tooling or platform problem that the current Three.js + physics approach cannot
reasonably solve.

## Candidate values are not release gates

A fixed physics step near 60 Hz, capsule dimensions, walk speed, slope/step
limits, camera pitch/boom distance, DPR cap and frame-time targets are tuning
seeds until the W1 fixture and physical devices provide evidence.

W1 PASS is based on invariants and comparative evidence, not arbitrary numeric
thresholds.

## W1 acceptance

W1 passes only when all of the following hold for the recorded candidate SHA and
test scope:

- one logical player and one active world renderer exist at a time;
- keyboard movement is camera-relative and does not penetrate the wall fixture;
- the fixture distinguishes accepted versus rejected slope/step cases according
  to its recorded configuration;
- camera obstruction handling prevents obvious wall/column camera penetration
  and recovers when the obstruction clears;
- simulation behavior is not tied directly to display refresh rate; 60/120 Hz
  comparison does not change world outcome beyond documented tolerance;
- pointer cancel/lost capture, blur, visibility suspension and reset cannot
  leave stuck movement;
- hidden/background time does not create catch-up movement on resume;
- semantic controls can reach the synthetic destination without dragging or
  walking;
- reduced-motion removes nonessential camera/ambient motion without removing
  the semantic route;
- forced renderer/context failure leaves the semantic controls usable;
- teardown drains task-owned listeners, timers, RAF loops, pending loads,
  physics ownership and live WebGL contexts;
- repeated start/stop/reset and world remount do not create unbounded owned
  resources;
- the Lab isolation/module-graph checks still prove that product
  API/Auth/Model V2 modules and W1-only dependencies are absent from the normal
  product path;
- a bounded physical Android Chrome check and physical iPhone/iPad Safari check
  demonstrate usable movement/camera input and clean stop/reset. Performance
  measurements are recorded before absolute budgets are promoted to gates.

## Local manual preview and live asset boundary

The dedicated automated Lab config remains on `127.0.0.1:4179`. Its pinned-asset
browser fixtures intercept the public URL with verified bytes; they prove
application behavior, not current live CORS for that origin.

For a manual preview with direct public asset loading, use the already permitted
local origin, keeping the server loopback-only and refusing an occupied port:

```bash
npm --prefix web/transcend-lab run build
npm --prefix web/transcend-lab run preview -- --host 127.0.0.1 --port 4173 --strictPort
```

Open `http://127.0.0.1:4173`, not `localhost` or an automatically incremented
port. As observed on 2026-09-25, the exact bear response includes
`Access-Control-Allow-Origin: http://127.0.0.1:4173`, but not for 4179 or 4187.
This is timestamped operational evidence, not a permanent CORS guarantee.
No bucket policy, gateway, credential, asset URL, proxy or deployment is changed.
Ctrl+C ends the foreground preview. A startup failure must not stop another
process to seize that port.

Playable simulation takes its first sample from the RAF callback, never from a
separate `performance.now()` sample during asynchronous mounting. Monotonic-time
validation remains enabled; a deliberately offset RAF regression checks that
initial loading cannot strand the renderer at its first frame.

## Camera framing and distance controls

The playable canvas uses CSS viewport pixels for its displayed size and keeps
DPR-scaled drawing-buffer pixels separate. The entry camera starts with a clear
boom and the bear facing away; the existing near-edge obstruction fixture remains
available for explicit collision checks. Camera defaults are tuning, not release budgets.

Movement remains camera-relative with independent Move/Look input ownership.
Looking while stationary does not rotate or translate the actor. Do not silently
replace this with steering or full-screen touch capture: native page pinch/scroll
outside the touch pads remains available. The focused world canvas accepts an
unmodified mouse wheel for bounded camera distance; modified wheels (including
browser zoom), unfocused canvas events and semantic controls retain native handling.
Camera closer/farther buttons provide touch and keyboard alternatives. Distance
requests still pass through the existing obstruction shape cast; Reset camera
restores the entry framing. The semantic destination and exit remain visible
while the additional camera controls are collapsed.
